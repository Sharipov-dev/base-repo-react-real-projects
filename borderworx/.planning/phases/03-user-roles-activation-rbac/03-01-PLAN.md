<objective>
Add the two auth-only backend endpoints that make the RBAC system usable:
`POST /api/auth/activate` (flips the authenticated user pending -> active) and
`GET /api/auth/me` (returns the current user's status + permissionKeys for FE gating).

Purpose: There is currently no code path that ever moves an invited user from `pending`
to `active`, so every WMS table returns `403 Account pending`. These endpoints close that gap.
Output: A new `findBySupabaseId` repo method, two use-cases, an AuthController, an auth-only
route file mounted at `/auth`, and full container wiring.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Spoofing | /api/auth/activate, /api/auth/me | mitigate | authMiddleware verifies the Supabase JWT before the handler runs; req.userId comes only from the verified token |
| T-03-02 | Tampering | /api/auth/activate | mitigate | Endpoint acts ONLY on req.userId (verified JWT subject). No user id is accepted from body/params, so a caller cannot activate another account |
| T-03-03 | Elevation of Privilege | ActivateUserUseCase | accept (by design, constrained) | Self-activation is the intended behavior, but strictly limited to pending -> active. Suspended/inactive users are returned unchanged; activation never grants permissions beyond the user's already-assigned role |
| T-03-04 | Information Disclosure | /api/auth/me | mitigate | Returns only the caller's own profile (keyed by req.userId); no cross-user lookup path exists |
</threat_model>
